# 援光 HelpLight — Demo 统一脚本（视频 + 图文帖）

> 用途：2–5 分钟录屏视频为主要载体；HF Discussion 图文帖复用同一叙事顺序，
> 截图按 `demo/SHOT-LIST.md` 逐张嵌入，正文口播要点可直接转成帖子段落文字。
> 素材原则：**全部画面与数据来自真实模型运行**（Spark-X2.6-4B 本地推理），
> 不用 stub 结果、不摆拍、不剪掉失败。总时长目标约 3 分 50 秒。
>
> 录制须知：当前录制环境为 2 核 VM，单条解析真实耗时约 90–125 秒、批量 3 条
> 约 5 分钟。等待段可加速播放，但**必须在画面上如实标注真实耗时**；正式录制
> 也可迁移到更快硬件，抽取内容不变、耗时数字按实际环境标注。

## ① 开场 — 问题与定位（约 30 秒）

- **画面**：先闪过一段「求助信息散落」的示意画面（群聊/社交平台风格的长文本
  滚动，均为虚构脱敏文本）→ 切到应用首页全貌（标题、边界声明、单条区、
  批量区、导出按钮）→ 边界声明字幕条定格。
- **口播要点**：灾害发生时，求助信息散落在社交平台、微信群和电话记录里，
  全是口语化长文本——地点、人数、需求、紧急程度、联系方式都埋在句子里，
  一线志愿者人工整理慢，还容易漏掉最紧急的那条。援光 HelpLight 做的事：
  把每条求助文本逐条抽成结构化字段，按紧急程度排成分诊清单，交给人复核
  后使用。抽取、研判、摘要全部由 Spark-X2.6-4B 在本地完成，不调用云端。
- **字幕要点（边界声明，必须出镜）**：「原型工具，不替代 110 / 119 / 120 与
  官方救援调度；模型抽取结果须经人工复核后使用；联系方式等个人信息仅在
  本机处理，不上传云端。」
- **真实输出文件**：无（界面本体 `app/static/index.html`；边界声明原文见
  `app/README.md` 开头）。

## ② 单条解析 — 洪涝示例逐字段讲解（约 70 秒）

- **画面**：在「① 单条求助解析」粘贴洪涝示例原文（或从示例载入）→ 点解析
  → 等待画面（加速播放，字幕标注「真实耗时约 2 分钟，2 核 VM」）→ 结果
  卡片出现，镜头逐字段停留高亮：地点 → 人数 → 人员构成 → 需求 → 紧急程度
  → 联系方式 → 中文摘要 → 英文摘要。
- **口播要点**：对照原文逐项验收——地点精确到「幸福里小区 3 号楼一楼」；
  人数 4（一家四口）；人员构成「两位老人，一个三岁小孩」没丢；需求三项
  （饮用水、食物、冲锋舟）全覆盖、无编造；紧急程度判「高」（被困 + 水淹
  一楼半 + 老人幼儿）；联系方式脱敏原样保留；中文摘要 40 字内准确；英文
  摘要供跨地区志愿者协作。8 个字段，一项不多、一项不少。
- **字幕要点**：「单条解析：8 字段一次抽取，全部由本地模型完成」。
- **真实输出文件**：`demo/outputs/parse-single-flood.json`（本次录制同批
  采集的 `/api/parse` 原始响应全文，帖子可附作运行证据）。

## ③ 批量分诊 — 3 条示例与导出（约 60 秒）

- **画面**：「② 批量分诊清单」点「一键载入 3 条示例」→ 点「解析全部并
  生成清单」（等待段加速，字幕标注真实总耗时）→ 排序后的清单表格全貌 →
  点「导出 Markdown」，打开导出的 `helplight-triage.md` 展示表格与原文
  列表 → CSV 文件在表格软件中一闪而过。
- **口播要点**：三条一起进来，出来就是一张排好序的清单，协调员从上往下
  处理即可。如实说明：这 3 条示例本次真实判定都是「高」，同级保持输入
  顺序；跨级排序另有真实证据——12 条评估样本全量批量时严格按 高 5 →
  中 4 → 低 3 输出、无一例错位，把输入顺序故意打乱后也被正确重排
  （评估报告第 5 节）。导出文件在浏览器端生成、不经过服务器，清单头部
  自带边界声明，文末附原文对照，方便转发与复核。
- **字幕要点**：「批量解析 → 按紧急程度排序 → 导出 Markdown / CSV」。
- **真实输出文件**：`demo/outputs/parse-batch-3examples.json`（`/api/parse-batch`
  原始响应）、`demo/outputs/helplight-triage.md`、`demo/outputs/helplight-triage.csv`
  （两份导出与前端 `buildMarkdown` / `buildCsv` 同格式生成，见 outputs/README）。

## ④ 诚实环节 — 已知失败案例 E12（约 45 秒）

- **画面**：并排展示 E12 捐赠咨询的**原文**与**模型输出原样**（结果卡或
  JSON）：原文是社区想**捐出**矿泉水和方便面、问送到哪里；输出里 needs
  却是「饮用水、方便面」，摘要把捐赠主语错安给安置点（「包河区淝河镇
  安置点拟捐赠……需对接送餐事宜」），英文摘要还有拼写错误
  「Ansettlement」。反转处圈注标红 → 切到人工标注的标准答案（needs 应为
  空——这是供给信息，不是需求）。
- **口播要点**：这是第一轮评估里最严重的一个错误：模型对「谁需要什么」
  的语义方向判反了，会把一条供给信息误登记成需求工单。我们不剪掉它，
  因为它正说明了本工具的定位——**抽取结果必须过人工复核这一关**，错误
  会在复核时显形，而不是被静默采用。同一轮评估的总账也如实公布：12 条
  样本 × 8 字段，严格准确率 74.0%、可用率 96.9%，紧急程度 12/12 全对，
  且没有任何一例虚构编造；主要短板是人员构成等细节会被压缩丢失。
- **字幕要点**：「已知局限：供给/咨询类文本可能出现语义方向错误 →
  人工复核不可省略（评估报告第 6 节）」。
- **真实输出文件**：`demo/outputs/parse-e12-donation.json`（本次复跑的
  `/api/parse` 原始响应）；v1 评估原始输出原稿在 `eval/results.json` 的
  E12 条目，原因分析见 `eval/EVAL-REPORT.md` 第 6 节案例 1。录制时以
  归档 JSON 的实际内容为准讲解，不背稿念数字之外的结论。

## ⑤ 收尾 — 本地运行与复现（约 25 秒）

- **画面**：回到应用首页全貌 → 一帧终端/健康检查画面（`/api/health`
  返回的本地端点与模型名）→ 复现命令字幕定格收尾。
- **口播要点**：全程本地运行、没有云端 API，灾区弱网和隐私敏感场景都能
  用。复现只需要一句话：本地 Ollama 加载官方 Spark-X2.6-4B（GGUF
  Q4_K_M），一条环境变量命令启动应用即可（帖子文末附完整步骤）。最后
  披露：本项目由 AI 辅助开发，抽取提示词与评估方法都在仓库中公开。
- **字幕要点**：「Spark-X2.6-4B 本地推理 · 零云端调用 · 步骤见帖子文末」。
- **真实输出文件**：`demo/outputs/README.md`（本批素材的生成命令、时间与
  模型版本记录）；完整复现步骤见 `eval/EVAL-REPORT.md` 第 10 节与
  `app/README.md`。
